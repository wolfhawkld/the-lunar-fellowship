# Lunar Lab Candidate · Living Memory Open Collaboration

> 状态：Candidate / 尚未激活
> 来源：[Lunar Session 01](../events/session-01-attention-living-memory-and-agency.md)
> 公开范围：Green
> 组织方式：一个共同命题，两条可独立启动、互相反馈的协作线

## 共同命题

当 AI 持续扩大信息与生成能力时，人的瓶颈越来越表现为注意力分配、上下文维护与长期记忆。`progressive-kg` 和 `living-memory` 已提供了一个值得共同验证的方向：用动态、三维、可成长的知识图谱，让阅读、思考、项目和人机协作形成的关系可以被持续保存、检验和重新唤起。

围绕这个命题，协作分为两个方向：

1. **产品 / 工具协作**：共同扩展 living-memory 本身的产品能力、工程实现和开源生态；
2. **共同知识数据图谱协作**：共同建设月曜同道会的知识数据图谱，把公开讨论、项目、问题、实验与来源连接为一份可持续演化的共同记忆。

两条线可以分别启动。产品线不应被单一社群数据锁死；知识图谱线也应保持数据可移植，不依赖某个工具才能存在。

## 协作线 A：产品 / 工具本身

### 目标

把 living-memory 从个人原型逐步发展为可使用、可扩展、可贡献的开放工具，重点验证它是否真正帮助用户恢复上下文、理解关系并管理注意力，而不只是展示更复杂的图形。

### 协作范围

- 明确 `progressive-kg` 与 `living-memory` 的关系、现有能力和技术边界；
- 梳理核心用户旅程：导入材料、形成关系、人工校正、追溯来源、重新进入旧问题；
- 改进数据模型、图谱生长机制、3D 交互和 Agent 协作接口；
- 建立可运行的开发环境、架构说明、Issue 结构和贡献指南；
- 在权属明确后选择许可证，并定义版本、评审与发布方式。

### 建议的首轮两周结果

首轮只选择一个最小闭环：

> 导入一组公开材料 → 形成可编辑的关系图 → 查看每条关系的来源 → 在后续问题中重新唤起相关上下文 → 导出可移植数据。

候选交付包括：

- 一页产品地图与架构草图；
- 一个可运行的最小 Demo；
- README、安装说明和 3–5 个适合新贡献者的 Issue；
- 对“线性笔记 / 静态图谱 / living memory”的一次小型任务对比。

### 首轮验证信号

- 使用者能否在不依赖作者讲解的情况下完成最小流程；
- 关系是否可编辑、可追溯，而不是由模型生成后无法判断依据；
- 再次进入旧主题时，是否更快恢复关键上下文；
- 新贡献者能否找到一个边界清楚、可以独立完成的任务。

## 协作线 B：共同知识数据图谱

### 目标

建设一份由成员共同维护、具有来源和演化历史的 Fellowship 知识数据图谱。它不是聊天记录全集，也不是成员画像库，而是一张围绕共同问题持续成长的认知地图。

首批内容可以来自已经公开的 Green 材料，例如活动摘要、项目提案、公开文章、来源链接、实验记录和明确允许共享的成员贡献。

### 建议的数据分层

- **Shared Green Core / 共同公开层**：经过确认、可以公开复用的来源、概念、问题、项目和实验；
- **Member-contributed Views / 成员贡献层**：成员主动选择贡献的节点、关系或个人视角，是否合入共同层由贡献者和图谱守护人共同确认；
- **Controlled Layer / 受控层**：可能包含 Amber 语境的材料，只有在访问控制、保存期限和退出机制另行设计后才考虑启用，不进入公开仓库。

共同图谱可以连接不同成员主动贡献的知识，但不默认集中同步个人笔记、聊天历史或私人知识库。

### 建议的数据对象

- **Source / 来源**：文章、书籍、公开链接、活动纪要或项目文档；
- **Concept / 概念**：讨论中需要持续澄清的关键词及其语境；
- **Claim / 判断**：当前形成但仍可被修订或反驳的认识；
- **Question / 问题**：尚未解决、值得继续探索的问题；
- **Project / 项目**：与问题相关的工具、实验或 Lunar Lab；
- **Experiment / 实验**：验证某个判断的方法、过程和结果。

默认不把“成员”作为需要公开建模的数据对象。确需标注贡献者时采用逐项 opt-in，并允许匿名、更正或从后续版本移除；公开仓库、历史版本和外部副本无法保证被完全回收，因此入库前必须明确告知。

### 建议的首轮两周结果

使用当前仓库中已经公开的材料，建立一份小型种子图谱：

- 覆盖初始提案、运营契约、Session 记录与 living-memory 候选 Lab；
- 每个节点和关系都能追溯到来源；
- 区分事实、观点、假设、问题和项目状态；
- 支持一次真实任务，例如回答“注意力问题如何演化为 living-memory 协作方向”；
- 提供可移植导出，避免共同知识被单一界面或实现锁定。

### 贡献与治理规则

- 只将 Green 内容纳入公开图谱；Amber 内容留在受控空间，Red 内容不进入 Fellowship；
- 每条判断保留来源、创建时间和修订历史，模型生成内容必须明确标识；
- 成员可以提出更正、合并、拆分或从当前公开版本移除的请求；已经发布的历史版本或外部副本无法承诺彻底删除；
- 引用成员观点、身份或原创材料前逐项获得许可；
- 不导入群聊全文，不建立未经同意的个人关系、兴趣或能力画像；
- 对外发布数据集前，单独确认内容许可、个人授权、更正与移除流程，以及公开后不可完全回收的风险。

### 首轮验证信号

- 成员能否从图谱中重新找到一次讨论的关键来源和未决问题；
- 不参加某次活动的人能否通过图谱理解议题如何发展；
- 成员能否低成本贡献一个节点、关系或修正；
- 数据质量、来源追踪和边界审查是否可以由多人共同维护。

## 两条协作线如何互相促进

```text
共同知识数据图谱 ── 提供真实场景、数据与治理要求 ──→ 产品 / 工具
        ↑                                              │
        └── 接收编辑、追溯、可视化与 Agent 能力反馈 ──┘
```

- 产品线把图谱协作需要的编辑、来源追踪、版本和可视化能力做成工具；
- 图谱线为产品提供真实但安全的使用场景，持续暴露数据模型与交互问题；
- 两条线共享一套最小数据契约和 Green 安全边界，但可以有不同节奏和推动者；
- 任一方向暂停时，另一方向的成果仍应可独立使用和导出。

## 分阶段规划

### Phase 0 · 对齐与盘点

- 画出两个现有项目的关系、代码与数据边界；
- 确认现有成果权属、可公开范围和许可证候选；
- 为两条协作线分别确定推动者、参与者和首轮结果；
- 定义最小共享数据契约，包括 ID、类型、关系、来源和状态。

### Phase 1 · 两周并行实验

- 产品线完成一个端到端最小流程；
- 图谱线基于仓库 Green 材料建立种子图谱；
- 用同一组数据完成一次联合演示；
- 记录实际帮助、维护成本、错误和边界问题。

### Phase 2 · 回看与开源决策

- 分别判断两条线是继续、缩小、调整还是停止；
- 如果继续，发布路线图、贡献指南、许可证和首批 Issue；
- 如果共同知识图谱需要非公开层，再单独设计访问控制与退出机制，不默认扩张公开范围。

## 建议角色

角色服务于首轮实验，不代表长期职位，当前均待认领：

- **Umbrella Convener / 总召集人**：维护共同命题与两条线之间的接口；
- **Product Lead / 产品线推动者**：收束产品范围和最小流程；
- **Graph Steward / 图谱守护人**：维护数据模型、来源和贡献质量；
- **Boundary Reviewer / 边界审阅者**：检查权属、许可、隐私与公开范围；
- **Contributors / 贡献者**：分别认领代码、设计、资料整理、数据录入或验证任务。

同一人可以兼任多个角色，但每条协作线至少需要一位明确推动者；没有推动者的方向继续保持 Candidate。

## 启动条件

每条协作线独立满足以下条件后即可启动，不必等待另一条线：

- 至少两位成员主动投入；
- 一位明确推动者负责收束范围；
- 一个两周内可展示的最小结果；
- 已确认所用代码、材料和数据的权属与分享范围；
- 约定回看时间，以及继续、调整或停止的判断方式。

## 当前需要成员确认

- 谁愿意推动产品 / 工具线，谁愿意推动共同知识数据图谱线；
- `progressive-kg` 与 `living-memory` 的关系及当前可公开资产；
- 首轮采用什么可移植数据格式和最小 Schema；
- 哪些现有 Green 文档进入种子图谱；
- 两条线各自选择哪个两周最小结果。

## 当前状态

本提案记录的是两个明确的协作方向及其候选规划，不代表任一方向已经启动，也不代表任何成员已经承诺投入。下一步是在 Lunar Chat 中分别认领推动者，并完成 Phase 0 的范围与边界确认。
