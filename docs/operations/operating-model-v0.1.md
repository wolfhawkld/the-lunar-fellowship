# The Lunar Fellowship 最小可运行机制 v0.1

> 状态：Draft / 待成员共创
> 建议试运行期：2026-07-25 至 2026-08-23
> 原则：先让连接发生，再用真实运行经验完善制度。

当前试运行基于三个现实假设：现有成员共八位；大家对 AI 话题有积极兴趣，但业余时间有限且不稳定；Lunar Chat 是最容易发生持续贡献的场域。因此首月采用 `Chat-first / Talk on demand / Work assisted`，不要求三种渠道同步成熟。

## 1. 这套机制要解决什么

早期阶段不需要建立复杂组织，而需要稳定完成三个动作：

1. 让成员能低压力地开始表达、提问和互相认识；
2. 让值得继续的话题从即时讨论进入同步交流；
3. 让交流形成可查找的结论、行动和协作项目。

它暂不追求：

- 建立完整层级、职位或审批流程；
- 让每一次聊天都被记录；
- 要求每位成员以同样方式、同样频率参与；
- 在第一次聚会中确定所有长期规则。

## 2. Chat、Talk、Work 的协作闭环

```text
                    ┌─ 有清晰问题、三人以上感兴趣 ─→ Lunar Talk
Lunar Chat 日常核心 ┤
                    └─ 有可复用认识、决定或行动 ─→ Lunar Work
                                  ↑                       │
                                  └──── 结果返回 Chat ────┘
```

### Lunar Chat：日常连接与信号发现

建议载体：正式微信群，群名可使用 `月曜同道会 · Lunar Chat`。

适合：

- 分享一个链接、一段观察、一个问题或一次 AI 实践；
- 快速反馈、约人继续聊、发布活动与项目动态；
- 通过投票或一句话回答了解成员兴趣。

不适合：

- 存放唯一版本的重要文档；
- 直接粘贴公司、客户或个人的敏感信息；
- 对复杂问题进行无限滚动、没有结论的长讨论。

约定：一段讨论如果出现了明确结论、可复用方法、待验证假设或后续行动，由发起者或当周记录者在 Lunar Work 留下一条简短沉淀。无需搬运全部聊天记录。

首月大多数成员只参与 Lunar Chat 就已经足够。群消息不要求实时阅读，不制造“需要补完所有历史消息”的压力，也不设置每周发言任务。

### Lunar Talk：同步交流与关系建立

建议载体：成员可低门槛加入的在线视频工具，以及线下场地。

适合：

- 由 Chat 中的真实兴趣触发的线上、线下或混合交流；
- 需要语境、追问和共同推演的话题；
- 成员介绍、主题分享、案例诊所和项目复盘。

除首次成员聚会外，Talk 不预设固定频率。一个话题同时满足以下条件时再组织：

- 有一个清晰、足够具体的问题；
- 至少三位成员明确表示愿意参加；
- 有一位成员愿意召集；
- 30 至 60 分钟能够产生某种认识或下一步。

Talk 不要求八位成员全部到场，未参加者也没有补课义务。

选择视频工具时，首场活动只检查以下条件：

- 公司内外成员都能通过链接加入；
- 在中国大陆常用网络和移动端环境中稳定；
- 支持屏幕共享、文字聊天和画廊视图；
- 不强制所有成员创建新的组织账号；
- 能稳定支持计划中的活动时长；
- 可以关闭默认录制。

首场活动不应被长期工具选型阻塞。先使用召集人最熟悉且成员进入成本最低的工具，活动后再评估。

### Lunar Work：长期记忆与协同行动

建议以当前 GitHub 仓库作为可公开内容的入口；仓库实际可见性需要确认。后续按材料敏感度补充其他受控空间。

适合：

- 愿景、规则、会议纪要和主题索引；
- 可公开或已脱敏的方法、案例和共识；
- Lunar Labs 的提案、任务、产出与复盘；
- 需要成员异步审阅和形成版本的内容。

每次沉淀优先回答四个问题：

1. 我们目前形成了什么认识？
2. 还有什么没有确定？
3. 下一步是什么？
4. 谁愿意继续推动，预计何时回看？

首月不要求所有成员学习 GitHub 工作流或亲自整理文档。由一至两位愿意承担的记录者把高价值内容压缩后放入 Work，成员只需在 Chat 中确认其理解是否准确。

### 与 Lunar Sessions、Lunar Labs 的关系

- `Lunar Sessions` 是正式或策划过的交流活动，可通过 Lunar Talk 线上、线下或混合举行。
- `Lunar Labs` 是有明确问题、参与者、周期和产出的实践项目，主要通过 Lunar Work 管理。
- Chat / Talk / Work 是协作方式；Sessions / Labs 是活动和项目，不需要互相替代。

## 3. 让偏内向成员逐步参与

成员不需要一开始就做公开分享。建议采用六级参与阶梯：

1. 表情回应或匿名/实名投票；
2. 回答一个一句话问题；
3. 在群里发布一个链接、观察或问题；
4. 与一至两位成员进行小组交流；
5. 做 60 秒自我介绍或 5 分钟轻分享；
6. 发起一次 Talk、Session 或 Lab。

所有层级都算有效参与，不以发言时长评价成员贡献。

具体机制：

- **先写后说**：重要讨论先给 1 至 2 分钟安静书写，再依次发言；
- **小组优先**：先两人或三人交流，再回到全体，降低第一次开口成本；
- **允许 Pass**：轮流发言时可以跳过，不临时点名要求即兴输出；
- **问题具体**：用“最近一次让你惊讶的 AI 使用是什么”代替“大家聊聊 AI”；
- **限制强者占用**：主持人控制单次发言时长，优先邀请尚未发言者；
- **不强制开摄像头**：参与质量不与摄像头状态绑定；
- **提前预热**：召集人邀请两至三位成员在建群后的前 48 小时率先发布真实、小而具体的内容。

## 4. 建议的早期节奏

首月保持轻量、可预期：

- 每周最多一个由召集人或成员提出的结构化问题，自然分享不受此限制；
- 每一至两周整理一次不超过五条的 Lunar Digest；没有值得总结的内容时可以跳过；
- Talk 由 Chat 中的兴趣触发，通常控制在 30 至 60 分钟；
- 首月回顾优先使用三个异步问题完成，只有确有必要才另开会议。

建议把参与拆成不同大小的时间单元：

- 10 秒：表情回应；
- 1 至 3 分钟：一句话回答或提出问题；
- 3 至 5 分钟：发布一条实践信号或链接说明；
- 5 至 15 分钟：回应他人或整理一次讨论；
- 30 至 60 分钟：自愿参加一次 Talk。

成员可以只选择其中一种，不存在默认的每周最低投入。

群聊不以消息量作为活跃指标。比消息量更重要的是：

- 是否有更多成员开始贡献问题或经验；
- 是否形成新的成员连接；
- 是否有讨论进入可验证的下一步；
- 是否出现第一个小型协作实验。

## 5. 最小角色

角色服务于一次活动或一个周期，不代表组织级别，建议轮换：

- **Convener / 召集人**：确认目标、时间、人员和最终推进；
- **Facilitator / 主持人**：照顾发言秩序、节奏和成员体验；
- **Bridge / 线上桥接人**：混合活动中关注线上成员、聊天区和技术状态；
- **Scribe / 记录者**：只记录结论、开放问题和下一步，不制作逐字稿；
- **Steward / 守护人**：维护成员边界、敏感信息提醒和新成员加入。

日常 Chat 阶段只需要一位召集人和一位可兼任的记录者。其他角色在 Talk、Session 或 Lab 实际发生时再启用，不提前制造职位和轮值负担。首次混合聚会至少应明确主持人、线上桥接人和记录者。

## 6. 跨公司协作的安全底线

以下是试运行期的操作底线，不替代任何成员与雇主之间的合同、制度或法律义务；如有冲突，以更严格的要求为准。

成员均以个人身份参与，不默认代表所在公司，也不因加入 Fellowship 获得任何公司、客户或其他成员内部信息的访问权。

### 信息分级

- **Green / 可公开**：公开链接、通用方法、个人原创且可公开的经验、已授权材料，可以进入 GitHub。
- **Amber / 限定范围**：已脱敏但仍带有业务语境的讨论，只在明确的 Fellowship 或具体 Lab 成员范围内交流；未经内容提供者同意，不转发、不截图、不录入公开仓库。
- **Red / 不进入 Fellowship**：公司或客户机密、未公开经营数据、个人信息、受限制代码或文档、访问凭据，以及成员无权分享的知识产权。

无法判断时，按更高敏感等级处理，并先询问材料所有者。

### 默认行为

- 分享真实问题时抽象公司名、客户名、项目名、数据和可识别细节；
- 不把公司或客户敏感信息粘贴到外部 AI 工具；
- 引用其他成员的观点、截图或材料前先获得同意；
- 会议默认不录音、不录像、不自动转写，也不接入 AI 会议机器人；确有需要时说明目的、访问者、保存范围和删除时间，并逐位获得同意；
- 对外发布共同成果前，确认作者、许可范围、是否代表 Fellowship，以及是否涉及成员雇主。

建议群公告使用一句易记的规则：

> 带走启发，不带走未经允许的内容；分享自己的判断，不分享无权分享的信息。

如发生误发敏感内容，成员应停止查看和转发，立即提醒发送者与当期守护人，在可行范围内删除副本；如涉及凭据或公司报告义务，由相关成员立即按所属组织的规则处理。

## 7. 成员与决策的轻量机制

### 成员加入

试运行期采用现有成员邀请制：

1. 邀请人向候选成员说明项目定位和安全底线；
2. 候选成员明确同意群规则；
3. 入群后使用统一介绍卡完成轻量自我介绍；
4. 不公开传播群二维码，避免成员边界失控。

成员可以随时降低参与频率或退出，无需解释个人原因。退出后仍应遵守对已接触非公开内容的约定。

### 决策

- 日常、低成本、可逆的尝试，由提出者说明目的和回看时间后直接试行；
- 涉及对外发布、费用、成员边界、长期规则或共同名义的事项，在 Lunar Work 留下提案，并至少开放 48 小时供成员提出实质异议；
- 如果存在重要异议，先缩小试验范围或延后，不追求用简单多数压过尚未解决的风险；
- 每项行动必须有一位明确推动者，没有推动者的想法保留为候选，不视为承诺。

## 8. 首月建议路线

### Week 0：建立连接

- 创建 Lunar Chat；
- 完成成员介绍卡；
- 在成员时间允许时举行 `Lunar Session 00` 首次轻量聚会；
- 形成一份初步成员兴趣地图。

### Week 1 至 2：让 Chat 自然形成节奏

- 发布一至两个真实、具体、无需长篇准备的问题；
- 整理首场聚会结论；
- 观察哪些话题能产生成员之间的自然回应；
- 不急于确定下一次 Talk，也不要求所有人形成固定贡献习惯。

### Week 3 至 4：按信号决定是否升级

如果一个话题满足 Talk 的触发条件，安排一次 30 至 60 分钟主题交流；否则继续以 Chat 为主，不把“没有开会”视为失败。

只有在两位以上成员主动愿意投入时，才考虑一个满足以下条件的 Lunar Lab：

- 不依赖敏感公司数据；
- 两至四人愿意投入；
- 两周内能产生一个可展示结果；
- 结果可以明确为公开、成员内共享或不留存。

试运行结束后，通过异步反馈或一次 30 分钟回顾形成 v0.2。

## 9. 当前待成员确认的事项

- 微信群名称与群主/管理员；
- 首场活动日期、线下地点和在线视频工具；
- GitHub 仓库的成员权限与公开范围；
- Amber 材料将存放在哪里；
- 新成员邀请是否需要两位现有成员确认；
- 首月 Digest 和会议记录由谁轮值；
- 哪些内容可以代表 Fellowship 对外发布。

## 10. v0.1 是否有效的观察信号

试运行结束时，不用人数或消息总量评价成败，观察以下信号：

- 大多数成员至少以一种低压力方式参与过；
- 群内出现成员之间的直接回应，而不只是回应召集人；
- 成员之间出现了自然的一对一或小组连接；
- 至少一次高价值讨论被沉淀为可查找的内容；
- 至少出现一个具备 Talk 潜力的共同话题；是否实际举行不作为硬指标；
- 有成员愿意继续发起分享、问题或小型验证；
- 没有发生未经同意的转发、录制或敏感信息扩散。
